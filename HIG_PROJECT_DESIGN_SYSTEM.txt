# HUMAN INTERFACE GUIDELINES — PROJECT DESIGN SYSTEM

## PURPOSE

При разработке и изменении интерфейса этого проекта необходимо следовать принципам Apple Human Interface Guidelines.

Цель — не буквально копировать интерфейс iOS, а создавать интерфейс с такими же качествами:

- ясность;
- визуальная иерархия;
- простота;
- предсказуемость;
- прямое взаимодействие;
- минимальная когнитивная нагрузка;
- естественная навигация;
- качественная типографика;
- понятная обратная связь;
- доступность;
- адаптивность;
- аккуратная анимация;
- ощущение глубины;
- отделение контента от элементов управления;
- единая дизайн-система.

Функциональность и понятность ВСЕГДА важнее декоративных эффектов.

Не добавлять визуальные элементы только ради красоты, если они:
- ухудшают читаемость;
- усложняют интерфейс;
- отвлекают от основного действия;
- мешают accessibility;
- создают неоднозначность;
- уменьшают производительность;
- затрудняют взаимодействие.

==================================================
1. ОСНОВНАЯ ФИЛОСОФИЯ
==================================================

Интерфейс должен ощущаться:

- лёгким;
- естественным;
- спокойным;
- современным;
- отзывчивым;
- последовательным;
- физически понятным;
- визуально целостным.

Каждый экран должен иметь очевидный ответ на вопросы:

1. Где я нахожусь?
2. Что здесь можно сделать?
3. Какое действие главное?
4. Что произойдёт после действия?
5. Как вернуться назад?
6. Что сейчас происходит?
7. Успешно ли завершилось действие?

Не заставлять пользователя изучать интерфейс.

Если элемент выглядит интерактивным — он должен быть интерактивным.

Если элементы выполняют одинаковую функцию — они должны выглядеть одинаково.

Если элементы выглядят одинаково — они должны вести себя одинаково.

==================================================
2. CONTENT FIRST
==================================================

Контент является главным уровнем интерфейса.

Навигация, toolbar, tab bar, floating controls и другие управляющие элементы являются отдельным уровнем над контентом.

Не превращать весь интерфейс в набор стеклянных карточек.

Не заключать каждый блок текста в отдельный контейнер без необходимости.

Использовать контейнер только тогда, когда он:

- объединяет связанную информацию;
- создаёт понятную группу;
- является интерактивным объектом;
- отделяет функционально разные области;
- необходим для визуальной иерархии.

Страница должна выглядеть как единая композиция, а не dashboard из десятков случайных прямоугольников.

==================================================
3. VISUAL HIERARCHY
==================================================

На каждом экране должно быть не более одного очевидного основного действия.

Иерархия:

PRIMARY
Главное действие текущего экрана.

SECONDARY
Дополнительные действия.

TERTIARY
Редкие или вспомогательные действия.

DESTRUCTIVE
Удаление, отмена, выход, необратимые действия.

Главное действие должно выделяться:
- положением;
- размером;
- контрастом;
- цветом;
- visual weight.

Не выделять несколько кнопок одинаково сильно.

Не использовать accent color повсюду.

Accent color должен сообщать:
- интерактивность;
- выбор;
- состояние;
- главное действие.

==================================================
4. LAYOUT
==================================================

Интерфейс должен быть адаптивным.

Нельзя проектировать только под одно разрешение.

Не использовать фиксированные координаты для основных элементов интерфейса.

Использовать:
- flex;
- grid;
- intrinsic sizing;
- min/max constraints;
- responsive containers;
- safe areas;
- fluid dimensions.

Контент должен корректно адаптироваться к:
- маленькому телефону;
- большому телефону;
- планшету;
- desktop/web;
- portrait;
- landscape;
- изменению размера окна;
- увеличенному системному тексту.

Не привязывать интерфейс к конкретной высоте viewport.

Избегать:
height: 100vh

если это может вызвать проблемы с mobile browser UI.

Предпочитать:
min-height;
dvh;
svh;
flex layout.

==================================================
5. SAFE AREA
==================================================

Никогда не помещать критический интерфейс вплотную к физическим краям экрана.

Учитывать:
- notch;
- Dynamic Island;
- status area;
- home indicator;
- browser controls;
- Telegram WebView controls;
- rounded display corners.

Для web поддерживать:

env(safe-area-inset-top)
env(safe-area-inset-right)
env(safe-area-inset-bottom)
env(safe-area-inset-left)

Bottom navigation не должна конфликтовать с home indicator.

Floating CTA не должна находиться слишком близко к нижней границе.

==================================================
6. SPACING SYSTEM
==================================================

PROJECT DEFAULT:

Использовать системный шаг 4 px.

Основные значения:

4  — минимальный микропромежуток
8  — маленький
12 — компактный
16 — стандартный
20 — увеличенный
24 — секционный
32 — большой
40 — крупный
48 — очень крупный
64 — разделение крупных секций

Предпочтительные значения:
8 / 12 / 16 / 20 / 24 / 32

Не использовать случайные значения:
13px
17px
19px
23px
27px

если для них нет конкретной причины.

Одинаковые типы элементов должны иметь одинаковые отступы.

==================================================
7. SCREEN PADDING
==================================================

PROJECT DEFAULT:

Mobile:
16px minimum horizontal padding.

Comfortable mobile:
16–20px.

Tablet:
20–28px.

Desktop:
24–40px в зависимости от layout.

Не растягивать текстовые блоки на всю ширину desktop.

Использовать max-width для контента.

==================================================
8. TYPOGRAPHY
==================================================

Типографика должна создавать иерархию без необходимости использовать десятки цветов.

Предпочитать системные шрифты.

Для web:

font-family:
-apple-system,
BlinkMacSystemFont,
"Segoe UI",
Roboto,
Helvetica,
Arial,
sans-serif;

Не подключать SF Pro как обычный web-font без проверки соответствующей лицензии.

Для Apple-устройств -apple-system автоматически использует системную типографику.

Основные текстовые уровни:

Large Title
Title
Title 2
Title 3
Headline
Body
Callout
Subheadline
Footnote
Caption

PROJECT DEFAULT для mobile web:

Large Title:
32–36px
font-weight: 700

Title:
26–30px
font-weight: 700

Title 2:
22–24px
font-weight: 600–700

Title 3:
19–21px
font-weight: 600

Headline:
17px
font-weight: 600

Body:
17px
font-weight: 400

Callout:
16px

Subheadline:
15px

Footnote:
13px

Caption:
12px

Это проектные параметры, а не требование воспроизводить нативные метрики iOS пиксель-в-пиксель.

==================================================
9. TEXT READABILITY
==================================================

Основной текст не должен быть слишком мелким.

Не использовать 11–12px как основной текст интерфейса.

Мелкий текст допустим только для:
- metadata;
- secondary labels;
- timestamps;
- captions.

Не использовать чрезмерно тонкие начертания.

Body text должен иметь комфортный line-height.

PROJECT DEFAULT:

Body:
line-height: 1.35–1.5

Headings:
line-height: 1.1–1.25

Не использовать ALL CAPS для длинного текста.

Не использовать слишком большой letter-spacing.

==================================================
10. DYNAMIC TYPE / TEXT SCALING
==================================================

Интерфейс должен переживать увеличение текста.

Нельзя рассчитывать, что текст всегда занимает одну строку.

Не устанавливать фиксированную высоту компонента, если внутри находится динамический текст.

Разрешать:
- перенос строки;
- увеличение высоты;
- перестройку layout.

Не обрезать важный текст через ellipsis без необходимости.

Кнопка с длинным названием должна иметь возможность расшириться.

==================================================
11. COLORS
==================================================

Использовать семантическую систему цветов.

Не привязывать смысл непосредственно к hex-коду.

ПЛОХО:

color: #ffffff
background: #000000

ЛУЧШЕ:

--color-label-primary
--color-label-secondary
--color-background-primary
--color-background-secondary
--color-fill
--color-separator
--color-accent
--color-destructive
--color-success
--color-warning

Цвет должен зависеть от роли элемента.

==================================================
12. SEMANTIC COLORS
==================================================

Создать токены:

--bg-primary
--bg-secondary
--bg-tertiary

--surface-primary
--surface-secondary
--surface-elevated

--label-primary
--label-secondary
--label-tertiary

--separator
--separator-strong

--accent
--accent-hover
--accent-active

--success
--warning
--destructive
--info

Каждый токен должен иметь light и dark variant.

Не использовать hardcoded white/black для всего приложения.

==================================================
13. DARK MODE
==================================================

Dark Mode не является простым инвертированием Light Mode.

В dark mode:

- сохранять визуальную иерархию;
- снижать чрезмерную яркость;
- избегать абсолютно белого текста везде;
- использовать несколько уровней поверхностей;
- обеспечивать контраст;
- не делать все поверхности одинаково чёрными;
- сохранять accent colors читаемыми.

Изображения, градиенты, тени и glass effects должны проверяться отдельно в dark mode.

==================================================
14. CONTRAST
==================================================

Контент должен оставаться читаемым:

- на светлом фоне;
- на тёмном фоне;
- поверх изображений;
- поверх blur;
- внутри glass surfaces.

Не полагаться только на opacity.

Если blur/material делает текст плохо читаемым:
увеличить контраст,
изменить material,
добавить корректную подложку
или отказаться от эффекта.

Красивый blur не имеет приоритета над читаемостью.

==================================================
15. LIQUID GLASS / MATERIALS
==================================================

Liquid Glass использовать как material для управляющего слоя интерфейса.

Подходящие элементы:

- navigation bar;
- tab bar;
- toolbar;
- floating controls;
- compact control groups;
- floating search;
- contextual actions;
- sheets;
- transient UI.

Не использовать Liquid Glass как фон каждой карточки.

Контентный слой и управляющий слой должны визуально отличаться.

Glass должен визуально реагировать на содержимое позади него.

Glass surface может использовать:

- translucency;
- backdrop blur;
- saturation;
- subtle border;
- highlight;
- specular response;
- restrained shadow;
- background adaptation.

Не делать glass похожим на белый полупрозрачный прямоугольник.

==================================================
16. GLASS IMPLEMENTATION FOR WEB
==================================================

PROJECT DEFAULT:

background:
rgba(...)

backdrop-filter:
blur(...) saturate(...)

-webkit-backdrop-filter:
blur(...) saturate(...)

Дополнительно допустимы:

subtle border
inset highlight
low-opacity shadow
background tint

Не использовать blur слишком большого радиуса.

Не делать одновременно:
сильный blur +
сильную border +
сильную glow +
сильную shadow.

Эффект должен быть тонким.

==================================================
17. GLASS ON GLASS
==================================================

Избегать большого количества вложенных glass surfaces.

ПЛОХО:

glass screen
  -> glass panel
      -> glass card
          -> glass button

Это уничтожает иерархию.

Предпочитать:

content background
  -> normal content
  -> floating glass navigation/control layer.

==================================================
18. CORNER RADIUS
==================================================

Использовать согласованную систему радиусов.

PROJECT DEFAULT:

small:
8px

control:
10–12px

card:
14–16px

large card:
18–20px

sheet:
20–28px

pill:
999px

Не использовать случайные разные радиусы на каждом элементе.

Вложенный компонент должен учитывать радиус родителя.

Если outer radius = R,
inner radius визуально должен соответствовать внутреннему расстоянию, а не быть случайным.

==================================================
19. BUTTONS
==================================================

Кнопка должна явно выглядеть интерактивной.

Основные типы:

PRIMARY
SECONDARY
TERTIARY
PLAIN
DESTRUCTIVE
ICON BUTTON

PRIMARY:
использовать для главного действия.

SECONDARY:
для альтернативного действия.

TERTIARY/PLAIN:
для менее важных действий.

DESTRUCTIVE:
для потенциально опасных действий.

Не использовать destructive red для обычных кнопок.

==================================================
20. TOUCH TARGET
==================================================

Для touch-интерфейса интерактивная область должна быть не менее примерно 44×44.

Важно:

визуальная иконка может иметь размер:
20–24px,

но hit area вокруг неё:
минимум около 44×44.

Это относится к:

- back;
- close;
- icon buttons;
- favorite;
- share;
- menu;
- checkbox;
- radio;
- tab item;
- compact controls.

На web 44 CSS px использовать как практический ориентир для touch target.

==================================================
21. BUTTON STATES
==================================================

Каждая кнопка должна иметь состояния:

default
hover
pressed / active
focus-visible
disabled
loading

Для touch:
pressed feedback обязателен.

Для desktop:
hover не должен быть единственным способом понять интерактивность.

Loading button:
- не должен запускать action повторно;
- должен показать progress;
- желательно сохранять ширину;
- не должен прыгать при смене текста.

==================================================
22. PRESSED FEEDBACK
==================================================

После tap пользователь должен сразу получить визуальную реакцию.

Допустимо:

opacity;
scale;
background change;
material response;
highlight.

PROJECT DEFAULT:

scale при tap:
примерно 0.97–0.99.

Не использовать чрезмерный bounce для обычных кнопок.

==================================================
23. ICONS
==================================================

Использовать единый icon family.

Не смешивать:

filled icons,
outline icons,
3D icons,
emoji,
разные visual weights

без причины.

Иконки должны быть:

- простыми;
- узнаваемыми;
- визуально сбалансированными;
- согласованными по stroke;
- согласованными по optical size.

Если интерфейс не является нативным Apple-приложением, не считать SF Symbols обязательными.

Можно использовать совместимую единую web icon system.

==================================================
24. ICON + LABEL
==================================================

Если смысл иконки может быть неоднозначным — использовать текстовую подпись.

Особенно для:

- tabs;
- unfamiliar actions;
- destructive actions;
- settings;
- complex navigation.

Не заставлять пользователя угадывать значение абстрактной иконки.

==================================================
25. NAVIGATION
==================================================

Навигационная модель должна быть предсказуемой.

Каждый экран должен иметь понятное место в hierarchy.

Типичная структура:

ROOT
  -> DETAIL
      -> SUBDETAIL

Back должен возвращать к предыдущему уровню.

Не использовать кнопку Back для перехода в произвольный другой раздел.

==================================================
26. TAB BAR
==================================================

Tab Bar использовать для основных независимых разделов приложения.

Tab Bar НЕ использовать для:
- действий;
- фильтров;
- изменения состояния;
- открытия modal;
- submit.

Tab — это destination.

Tab item должен иметь:
- icon;
- короткую label;
- active state.

Не менять расположение tabs между экранами.

Основная навигация должна быть стабильной.

==================================================
27. NUMBER OF TABS
==================================================

Сохранять небольшое количество основных разделов.

Не превращать bottom navigation в список из десятка функций.

Если раздел второстепенный:
поместить его внутрь соответствующего раздела или More/Profile/Settings structure.

==================================================
28. NAVIGATION BAR
==================================================

Navigation bar может содержать:

leading:
Back / Close

center:
Title

trailing:
contextual actions

Не перегружать navbar.

Самое важное содержимое должно оставаться контентом, а не набором кнопок в header.

==================================================
29. LARGE TITLES
==================================================

Large title допустим для корневых экранов.

При scroll заголовок может становиться компактнее.

Не использовать огромные заголовки на каждом nested screen.

Detail screen обычно должен иметь более компактную hierarchy.

==================================================
30. SEARCH
==================================================

Поиск должен быть очевидным.

Search field должен иметь:

search icon;
placeholder;
clear action;
text input;
focus state.

При необходимости:
recent searches;
suggestions;
popular queries;
filters.

Не запускать expensive request на каждый символ без debounce.

PROJECT DEFAULT:
debounce около 200–400 ms,
если архитектура поиска требует сетевых запросов.

==================================================
31. LISTS
==================================================

Связанную информацию предпочтительно отображать списком.

Каждая строка должна иметь понятную структуру.

Пример:

leading
    icon / avatar

content
    title
    subtitle

trailing
    value / badge / chevron

Не размещать слишком много независимых действий внутри одной строки.

==================================================
32. CHEVRONS
==================================================

Chevron означает переход глубже.

Не использовать chevron как декоративную иконку.

Если строка не открывает другой экран/уровень — chevron обычно не нужен.

==================================================
33. CARDS
==================================================

Карточка должна представлять самостоятельную логическую сущность.

Например:

- специалист;
- запись;
- товар;
- событие;
- результат поиска.

Карточка не должна использоваться только потому, что дизайнер хочет добавить rounded rectangle.

Не делать:
card inside card inside card.

==================================================
34. FORMS
==================================================

Формы должны быть максимально короткими.

Не спрашивать информацию раньше, чем она действительно нужна.

Поля логически группировать.

Порядок должен соответствовать естественному процессу.

Label не должен исчезать полностью после ввода текста, если пользователь может забыть назначение поля.

Placeholder не является полноценной заменой label для сложных форм.

==================================================
35. TEXT FIELDS
==================================================

Text field должен иметь:

label при необходимости;
input;
placeholder;
focus state;
error state;
disabled state;
optional helper text.

Если поле имеет ошибку:
показывать конкретную причину.

ПЛОХО:
"Ошибка"

ХОРОШО:
"Введите номер телефона полностью"

Не очищать введённые данные при ошибке.

==================================================
36. KEYBOARD
==================================================

Использовать подходящий input type.

email:
type=email

phone:
type=tel

number:
inputmode=numeric

search:
type=search

URL:
type=url

Не заставлять пользователя переключать клавиатуру вручную.

==================================================
37. VALIDATION
==================================================

Не показывать агрессивную ошибку до того, как пользователь успел закончить ввод.

Использовать validation:

- после blur;
- после submit;
- в реальном времени только там, где это действительно помогает.

Ошибку отображать рядом с соответствующим полем.

==================================================
38. PICKERS / SELECTION
==================================================

Если вариантов мало:
использовать segmented control / radio / direct selection.

Если вариантов много:
list / searchable picker / sheet.

Не использовать dropdown для 2 вариантов, если можно показать их напрямую.

==================================================
39. TOGGLES
==================================================

Toggle должен изменять состояние сразу.

Примеры:

Notifications ON/OFF
Dark Mode ON/OFF
Public profile ON/OFF

Не использовать toggle для действия вроде:

"Удалить аккаунт"
"Сохранить"
"Отправить"

==================================================
40. SEGMENTED CONTROL
==================================================

Segmented control использовать для небольшого количества взаимоисключающих режимов одного контекста.

Например:

Все | Активные | Завершённые

Не использовать его как основную навигацию всего приложения.

==================================================
41. SHEETS
==================================================

Sheet использовать для задачи, тесно связанной с текущим экраном.

Примеры:

выбор даты;
фильтры;
редактирование;
быстрое действие;
confirmation;
создание записи.

Sheet должен ощущаться временным контекстом.

Не превращать каждый экран приложения в modal sheet.

==================================================
42. MODALS
==================================================

Modal использовать только если необходимо сфокусировать пользователя на отдельной задаче.

Не открывать modal ради информации, которую можно показать inline.

Modal должен иметь очевидный способ закрытия.

Если пользователь ввёл важные данные, случайное закрытие не должно бесследно уничтожать их.

==================================================
43. ALERTS
==================================================

Alert использовать для действительно важной информации.

Не использовать alert для:

"Данные сохранены"
"Добро пожаловать"
"Вы открыли страницу"

Такие сообщения лучше показывать ненавязчиво.

Alert оправдан когда требуется:
- решение;
- подтверждение;
- критическое предупреждение;
- разрешение значимого конфликта.

==================================================
44. DESTRUCTIVE ACTIONS
==================================================

Для необратимых действий:

- использовать destructive styling;
- ясно назвать действие;
- объяснить последствия;
- потребовать подтверждение, если цена ошибки высокая.

ПЛОХО:
"Вы уверены?"

ЛУЧШЕ:
"Удалить запись?"

Дополнительный текст:
"Это действие нельзя отменить."

Buttons:
Отмена
Удалить

==================================================
45. MENUS
==================================================

Context menu подходит для дополнительных действий.

Наиболее частые действия не прятать в меню.

Primary action должен быть доступен непосредственно.

Меню использовать для:
- secondary actions;
- rare actions;
- contextual actions.

==================================================
46. FEEDBACK
==================================================

Каждое действие пользователя должно иметь реакцию.

Tap -> pressed state.

Submit -> progress.

Success -> confirmation.

Failure -> explanation.

Long operation -> progress indicator.

Selected item -> selected state.

Не оставлять интерфейс визуально без реакции.

==================================================
47. LOADING
==================================================

Для короткого ожидания:
spinner / activity indicator.

Для загрузки контента:
skeleton может быть предпочтительнее.

Для длительной определимой операции:
progress indicator.

Не показывать fake progress.

Не блокировать весь экран, если пользователь может продолжить работу.

==================================================
48. SKELETONS
==================================================

Skeleton должен приблизительно соответствовать будущему layout.

Не делать skeleton сложнее контента.

Не использовать слишком агрессивные shimmer animations.

Учитывать prefers-reduced-motion.

==================================================
49. EMPTY STATES
==================================================

Пустое состояние должно объяснять:

1. Что здесь будет?
2. Почему сейчас пусто?
3. Что пользователь может сделать?

Пример:

"У вас пока нет записей"

"После бронирования они появятся здесь."

[Найти специалиста]

Не показывать просто пустой экран.

==================================================
50. ERROR STATES
==================================================

Ошибка должна сообщать:

- что произошло;
- что пользователь может сделать;
- можно ли повторить действие.

ПЛОХО:
Error 500.

ЛУЧШЕ:
"Не удалось загрузить записи."

[Повторить]

Technical details можно логировать отдельно.

==================================================
51. OFFLINE STATE
==================================================

Если сеть отсутствует:

не показывать бесконечный spinner.

Показать понятное состояние:

"Нет подключения к интернету."

Предоставить retry.

Если возможно:
показывать кэшированные данные.

==================================================
52. SUCCESS
==================================================

Не использовать alert для каждого успешного действия.

Подходящие способы:

- state update;
- checkmark;
- inline confirmation;
- subtle toast;
- haptic feedback в native environment.

Success animation должна быть короткой.

==================================================
53. MOTION
==================================================

Анимация должна объяснять изменение интерфейса.

Основные задачи motion:

- показать связь экранов;
- показать появление элемента;
- сохранить spatial context;
- подтвердить действие;
- показать hierarchy;
- направить внимание.

Не использовать анимацию исключительно ради демонстрации возможностей.

==================================================
54. ANIMATION DURATION
==================================================

PROJECT DEFAULT для UI:

micro interaction:
100–180ms

standard transition:
180–300ms

sheet/modal:
250–400ms

complex transition:
300–500ms

Не превращать обычную навигацию в длинную cinematic animation.

==================================================
55. EASING
==================================================

Избегать линейной анимации интерфейса.

Использовать естественное acceleration/deceleration.

Для появления:
ease-out.

Для исчезновения:
ease-in / fast ease.

Для перемещения:
smooth ease / spring.

Spring использовать умеренно.

==================================================
56. CONTINUITY
==================================================

Объекты должны визуально сохранять связь между состояниями.

Если карточка открывает detail:
по возможности переход должен ощущаться как продолжение выбранного объекта, а не случайная новая сцена.

Motion должен помогать пользователю понимать:
откуда появился экран
и куда он исчез.

==================================================
57. REDUCED MOTION
==================================================

Обязательно учитывать:

prefers-reduced-motion: reduce

При reduced motion:

- отключать parallax;
- сокращать масштабирование;
- исключать интенсивные spring animations;
- уменьшать перемещения;
- заменять сложные переходы fade transition.

Функциональность не должна зависеть от анимации.

==================================================
58. GESTURES
==================================================

Не делать скрытый gesture единственным способом выполнить важное действие.

Основные действия должны иметь видимый UI.

Swipe можно использовать как ускоренный способ:

- back;
- delete;
- archive;
- secondary actions.

Но альтернативный видимый путь должен существовать.

==================================================
59. SCROLL
==================================================

Scroll должен ощущаться естественно.

Не ломать нативную прокрутку без веской причины.

Не использовать aggressive scroll hijacking.

Не блокировать вертикальный scroll ради декоративной анимации.

Sticky/floating UI не должен занимать слишком много экрана.

==================================================
60. PULL TO REFRESH
==================================================

Использовать только если контент действительно имеет смысл обновлять вручную.

Не использовать refresh как замену правильной синхронизации данных.

==================================================
61. ACCESSIBILITY
==================================================

Accessibility является частью архитектуры, а не финальной проверкой.

Каждый экран должен работать для пользователей с:

- ограниченным зрением;
- colour vision differences;
- увеличенным текстом;
- screen reader;
- reduced motion;
- keyboard navigation;
- switch/assistive interaction.

==================================================
62. SCREEN READERS
==================================================

Все важные интерактивные элементы должны иметь доступное имя.

Icon-only button:

ПЛОХО:
<button><svg /></button>

НУЖНО:
aria-label="Закрыть"

Decorative icons:
aria-hidden="true".

Image content:
осмысленный alt.

Decorative image:
alt="".

==================================================
63. SEMANTIC HTML
==================================================

Использовать настоящие элементы:

button
input
label
nav
main
header
section
article
ul
li

Не создавать кнопку через:

<div onclick="...">

если можно использовать:

<button>.

Семантика важна для:
- keyboard;
- accessibility;
- screen readers;
- focus;
- browser behavior.

==================================================
64. KEYBOARD ACCESSIBILITY
==================================================

Интерфейс должен работать без мыши.

Обеспечить:

Tab navigation;
Shift+Tab;
Enter;
Space;
Escape для подходящих компонентов;
arrow keys там, где это ожидается.

Не ломать естественный tab order.

==================================================
65. FOCUS
==================================================

Не отключать outline без замены.

Использовать:

:focus-visible

Focus state должен быть хорошо заметен.

При открытии modal focus должен перейти внутрь него.

После закрытия focus желательно возвращать на вызвавший элемент.

==================================================
66. COLOR IS NOT ENOUGH
==================================================

Нельзя передавать информацию только цветом.

ПЛОХО:

зелёный = success
красный = error

без дополнительных признаков.

Добавлять:
- icon;
- text;
- shape;
- label.

==================================================
67. ACCESSIBLE TARGETS
==================================================

Даже если иконка маленькая, interaction area должна оставаться большой.

Соседние interactive targets не должны быть расположены настолько близко, чтобы пользователь часто нажимал не туда.

==================================================
68. PRIVACY
==================================================

Запрашивать только действительно необходимые данные.

Не просить permission заранее без контекста.

Сначала объяснить пользователю, зачем функция нужна.

Затем запросить разрешение в момент, когда пользователь пытается использовать соответствующую функцию.

Не использовать dark patterns.

==================================================
69. PERMISSIONS
==================================================

ПЛОХО:

При первом запуске подряд запросить:

location;
camera;
contacts;
notifications.

ХОРОШО:

Пользователь нажал:
"Определить моё местоположение"

-> объяснить пользу при необходимости
-> запросить location.

==================================================
70. USER CONTROL
==================================================

Пользователь должен контролировать интерфейс.

Не выполнять неожиданно необратимые действия.

Не перенаправлять без очевидной причины.

Не включать настройки без согласия.

Не подписывать пользователя автоматически.

Не скрывать способы отмены.

==================================================
71. UNDO
==================================================

Для обратимых действий предпочтительно дать возможность Undo вместо лишнего confirmation.

Например:

"Запись удалена"

[Отменить]

если действие технически может быть восстановлено.

==================================================
72. WRITING / MICROCOPY
==================================================

Текст интерфейса должен быть:

- коротким;
- человеческим;
- конкретным;
- понятным;
- нейтральным.

ПЛОХО:
"Произошла непредвиденная ошибка при выполнении операции"

ЛУЧШЕ:
"Не удалось сохранить изменения."

Кнопки должны описывать действие.

ПЛОХО:
OK
Yes

ЛУЧШЕ:
Сохранить
Удалить
Продолжить
Отменить

==================================================
73. BUTTON TEXT
==================================================

Начинать название действия с понятного глагола там, где это естественно:

Сохранить
Записаться
Добавить
Отправить
Выбрать
Продолжить

Не писать длинное предложение внутри кнопки.

==================================================
74. LOCALIZATION
==================================================

Не рассчитывать на фиксированную длину текста.

Другой язык может увеличить строку на 30–100%.

Layout должен выдерживать это.

Не встраивать текст в изображения.

Не строить ширину кнопки исключительно под одну русскую фразу.

==================================================
75. RTL
==================================================

Архитектура должна позволять поддержку right-to-left interfaces.

Использовать logical CSS properties где возможно:

margin-inline
padding-inline
inset-inline

вместо жёсткой зависимости от left/right.

==================================================
76. IMAGES
==================================================

Изображение должно иметь цель.

Не добавлять decorative image, если оно ухудшает hierarchy.

Для пользовательского контента использовать корректный aspect-ratio и object-fit.

Не растягивать изображения.

Не изменять aspect ratio.

==================================================
77. AVATARS
==================================================

Avatar обычно отображать круглым, если это фотография человека.

Использовать fallback:
initials / neutral placeholder.

Не показывать broken image.

==================================================
78. PERFORMANCE
==================================================

Премиальный UI должен быть быстрым.

Не считать heavy animation признаком качества.

Поддерживать:
- lazy loading;
- image optimization;
- GPU-friendly transforms;
- limited blur areas;
- efficient DOM;
- minimal layout thrashing.

Для animations предпочтительно:
transform
opacity

вместо постоянной анимации:
width
height
top
left.

==================================================
79. BLUR PERFORMANCE
==================================================

backdrop-filter дорог для рендеринга.

Не создавать десятки одновременно анимируемых backdrop-filter layers.

Особенно внимательно тестировать:
- старые iPhone;
- Android WebView;
- Telegram WebView;
- low-power devices.

При необходимости создавать graceful fallback.

==================================================
80. RESPONSIVE DESIGN
==================================================

Mobile first.

Но desktop не должен выглядеть как растянутый телефон.

На большом экране разрешается:

- увеличить max-width;
- использовать columns;
- split views;
- side panels;
- дополнительную contextual information.

При этом interaction model должен оставаться знакомым.

==================================================
81. BREAKPOINTS
==================================================

Не ориентироваться исключительно на названия устройств.

Breakpoints определять исходя из того, когда layout перестаёт помещаться.

Допустимые PROJECT DEFAULT starting points:

< 480
compact mobile

480–767
large mobile

768–1023
tablet

>= 1024
desktop

Но компонент должен быть responsive самостоятельно, а не только через глобальные media queries.

==================================================
82. CONTENT WIDTH
==================================================

Не растягивать длинный текст на весь desktop.

PROJECT DEFAULT:

text content:
max-width примерно 640–760px

main application content:
может быть шире.

Cards/grid:
адаптировать через minmax().

==================================================
83. Z-INDEX
==================================================

Создать централизованную шкалу.

PROJECT DEFAULT:

content: 0
sticky: 10
navigation: 20
dropdown: 30
overlay: 40
modal: 50
toast: 60

Не использовать случайные:

z-index: 9999999

==================================================
84. DESIGN TOKENS
==================================================

Все повторяющиеся значения вынести в tokens.

Минимальные категории:

colors
spacing
radius
typography
shadows
materials
motion
z-index
breakpoints.

Не дублировать одинаковые значения по десяткам компонентов.

==================================================
85. COMPONENT SYSTEM
==================================================

Создать reusable components:

Button
IconButton
Input
SearchField
TextArea
Select
Toggle
SegmentedControl
Avatar
Badge
Card
ListItem
NavigationBar
TabBar
Sheet
Modal
Alert
Toast
Skeleton
EmptyState
ErrorState
Spinner
Divider

Не создавать новый визуальный вариант компонента для каждого экрана.

==================================================
86. COMPONENT API
==================================================

Компоненты должны иметь semantic variants.

Пример:

Button
variant:
primary
secondary
tertiary
destructive

size:
small
medium
large

state:
loading
disabled

Не использовать props типа:

purpleButton=true
bigRoundedButton=true.

Design API должен описывать смысл, а не внешний вид.

==================================================
87. STATES
==================================================

Каждый компонент необходимо проверить в состояниях:

default
hover
focus
active
disabled
loading
error
selected

где соответствующее состояние имеет смысл.

==================================================
88. CONTENT STATES
==================================================

Каждый data-driven screen проверить:

loading
loaded
empty
partial
error
offline

Нельзя реализовать только ideal success state.

==================================================
89. TAB BAR + LIQUID GLASS
==================================================

Современная bottom navigation может ощущаться плавающей над контентом.

Разрешается:

- translucent material;
- background blur;
- subtle border/highlight;
- adaptive tint;
- elevated separation.

Контент может визуально продолжаться позади navigation layer.

Однако tap targets должны оставаться ясными и контрастными.

==================================================
90. FLOATING CONTROLS
==================================================

Floating controls должны:

- иметь конкретную функцию;
- не закрывать важный контент;
- учитывать safe area;
- иметь достаточно большой hit target;
- визуально отделяться от контента.

Не заполнять экран floating pills.

==================================================
91. BADGES
==================================================

Badge использовать для короткой status/count информации.

Примеры:

3
Новое
Активно

Не помещать длинные предложения в badge.

==================================================
92. STATUS COLORS
==================================================

Создать одинаковые правила:

success
warning
error
info
neutral

Одинаковый статус должен выглядеть одинаково во всём приложении.

==================================================
93. DIVIDERS
==================================================

Divider использовать умеренно.

Сначала разделять элементы через:
- spacing;
- grouping;
- typography.

И только потом через линии.

Не превращать интерфейс в таблицу Excel из separator lines.

==================================================
94. SHADOWS
==================================================

Тени должны помогать hierarchy.

Не использовать сильную shadow на каждом компоненте.

В dark mode shadow может быть почти незаметной — hierarchy можно создавать через surface contrast и material.

==================================================
95. GRADIENTS
==================================================

Gradient не должен ухудшать читаемость.

Не использовать множество разноцветных градиентов без системной причины.

Brand gradient использовать последовательно.

==================================================
96. ACCENT COLOR
==================================================

Accent является ограниченным ресурсом.

Использовать accent для:

- primary actions;
- selected controls;
- active navigation;
- links;
- important interaction feedback.

Если почти всё accent-colored — accent больше ничего не выделяет.

==================================================
97. BRANDING
==================================================

HIG не означает отсутствие бренда.

Brand может выражаться через:

- accent color;
- typography hierarchy;
- imagery;
- motion personality;
- illustrations;
- iconography;
- subtle material treatment.

Но branding не должен ломать привычные interaction patterns.

==================================================
98. MICROINTERACTIONS
==================================================

Разрешены:

button press
favorite animation
toggle animation
selection animation
loading transition
success feedback
card expansion

Но каждая microinteraction должна быть:
короткой,
понятной,
связана с действием.

==================================================
99. HAPTICS
==================================================

Если проект запускается в native environment и доступен haptic feedback:

использовать для:
- confirmation;
- important selection;
- warning;
- meaningful state changes.

Не генерировать haptic на каждый scroll/tap.

Для web отсутствие haptics не должно ухудшать usability.

==================================================
100. TOASTS
==================================================

Toast подходит для небольших transient confirmations.

Например:

"Ссылка скопирована"
"Изменения сохранены"

Не использовать toast для critical information.

Critical information должна оставаться видимой до принятия решения.

==================================================
101. PROGRESSIVE DISCLOSURE
==================================================

Не показывать все возможности одновременно.

Сначала показывать наиболее важные.

Дополнительные настройки раскрывать по мере необходимости.

Пример:

Основные параметры
Дополнительные параметры >

Это уменьшает cognitive load.

==================================================
102. ONBOARDING
==================================================

Не делать длинный onboarding, если интерфейс можно сделать понятным без него.

Не объяснять очевидные элементы.

Onboarding нужен только для:
- уникальной концепции;
- сложного workflow;
- критически важной настройки.

Пользователь должен иметь возможность пропустить необязательное обучение.

==================================================
103. FIRST LAUNCH
==================================================

Первый экран должен как можно быстрее приводить пользователя к ценности продукта.

Не начинать приложение с:

5 onboarding screens
-> registration
-> permissions
-> survey
-> notifications prompt

если это не необходимо.

==================================================
104. CONFIRMATION
==================================================

Не требовать подтверждение каждого действия.

Confirmation нужен, когда:
- действие разрушительное;
- действие дорогостоящее;
- последствия сложно отменить;
- вероятность случайного действия значима.

==================================================
105. RESPONSIVENESS
==================================================

После нажатия UI должен реагировать визуально практически сразу.

Если network operation занимает время:
не ждать ответ сервера перед показом feedback.

Сразу показать:
loading / optimistic state / progress.

==================================================
106. OPTIMISTIC UI
==================================================

Использовать optimistic UI только если ошибку можно безопасно откатить.

Например:
favorite
toggle preference
simple status update.

Для критических операций:
payment
booking confirmation
irreversible action

не показывать ложный success до подтверждения сервера.

==================================================
107. SCROLL POSITION
==================================================

При возврате назад желательно сохранять:

- scroll position;
- filter state;
- query;
- selected tab;
- relevant context.

Пользователь не должен начинать путь заново.

==================================================
108. DEEP NAVIGATION
==================================================

Не создавать избыточно глубокую hierarchy.

Если для обычной задачи нужно:

Home
-> Category
-> Subcategory
-> Group
-> List
-> Item
-> Action

проверить архитектуру.

Сокращать количество шагов.

==================================================
109. PRIMARY ACTION PLACEMENT
==================================================

Primary action должен быть легко доступен.

На mobile при длинной форме допустим sticky/floating bottom CTA.

Он должен учитывать safe area.

Не закрывать содержимое последнего элемента формы.

==================================================
110. ONE-HAND USE
==================================================

Часто используемые mobile actions по возможности размещать в комфортной зоне взаимодействия.

Не помещать все основные действия исключительно в верхние углы.

При этом системные навигационные patterns сохранять предсказуемыми.

==================================================
111. CONTENT PRIORITY
==================================================

Если экран перегружен:

не уменьшать всё подряд.

Сначала определить:
- что самое важное;
- что второстепенное;
- что можно спрятать;
- что можно удалить.

Hierarchy решает перегрузку лучше, чем уменьшение текста.

==================================================
112. WEB-SPECIFIC HIG ADAPTATION
==================================================

Проект является web-интерфейсом, поэтому не нужно имитировать iOS настолько буквально, чтобы нарушать web expectations.

Сохранять native web behavior:

- links работают как links;
- buttons как buttons;
- text можно выделять;
- forms работают с browser autofill;
- keyboard navigation работает;
- browser Back не ломает приложение;
- URLs отражают состояние там, где это возможно.

Использовать HIG как систему UX-принципов, а не как визуальную тему.

==================================================
113. TELEGRAM MINI APP / WEBVIEW ADAPTATION
==================================================

Если приложение работает внутри Telegram WebView:

учитывать:
- ограниченную высоту viewport;
- safe area;
- изменение viewport при клавиатуре;
- Telegram theme;
- mobile touch;
- Android и iOS;
- WebView performance;
- browser history limitations;
- opening/closing keyboard;
- bottom controls.

Не предполагать, что WebView всегда равен window.innerHeight.

Не размещать важные элементы непосредственно под Telegram chrome.

==================================================
114. DESIGN REVIEW RULE
==================================================

Перед завершением любого экрана проверить:

[ ] Понятно ли назначение экрана за 2–3 секунды?
[ ] Очевидно ли главное действие?
[ ] Есть ли визуальная hierarchy?
[ ] Нет ли лишних контейнеров?
[ ] Нет ли слишком большого количества glass?
[ ] Есть ли touch targets >= ~44x44?
[ ] Работает ли dark mode?
[ ] Работает ли увеличенный текст?
[ ] Есть ли keyboard navigation?
[ ] Есть ли visible focus?
[ ] Есть ли loading state?
[ ] Есть ли empty state?
[ ] Есть ли error state?
[ ] Есть ли disabled state?
[ ] Есть ли feedback после tap?
[ ] Учтён ли reduced motion?
[ ] Учтены ли safe areas?
[ ] Работает ли экран на узком устройстве?
[ ] Работает ли на широком экране?
[ ] Нет ли случайных цветов?
[ ] Нет ли случайных spacing values?
[ ] Нет ли случайных radii?
[ ] Все ли компоненты используют design tokens?
[ ] Не используется ли цвет как единственный сигнал?
[ ] Понятны ли icon-only actions?
[ ] Не скрыто ли основное действие в menu?
[ ] Не используется ли modal без необходимости?
[ ] Не используется ли alert для обычного success?
[ ] Не слишком ли много animations?
[ ] Не блокирует ли motion usability?

==================================================
115. ANTI-PATTERNS — NEVER DO THIS
==================================================

Не:

- делать все поверхности стеклянными;
- делать card внутри card внутри card;
- использовать gradient на всём;
- использовать glow на всём;
- делать маленькие tap targets;
- использовать 12px для основного текста;
- смешивать icon styles;
- использовать 5 primary buttons;
- прятать важное действие в меню;
- использовать modal для каждого шага;
- использовать alert вместо нормального UI;
- делать scroll hijacking;
- использовать длинные animations;
- блокировать accessibility;
- удалять focus outline без замены;
- использовать div вместо button;
- hardcode light mode colors;
- передавать status только цветом;
- запрашивать permissions без контекста;
- показывать бесконечный loader;
- очищать форму после validation error;
- менять navigation structure между экранами;
- использовать случайные spacing/radius values;
- перегружать экран декоративными элементами.

117. FINAL IMPLEMENTATION PRINCIPLE
==================================================

При любом выборе между:

"выглядит эффектнее"

и

"понятнее пользователю"

выбирать понятнее пользователю.

При выборе между:

"больше декоративных элементов"

и

"лучше hierarchy"

выбирать hierarchy.

При выборе между:

"кастомное необычное поведение"

и

"привычное предсказуемое поведение"

по умолчанию выбирать привычное.

При выборе между:

"сложная анимация"

и

"быстрый интерфейс"

выбирать быстрый интерфейс.

При выборе между:

"копировать iOS"

и

"следовать принципам HIG"

следовать принципам HIG.

==================================================
118. RULE FOR AI / CODEX
==================================================

При создании нового UI:

1. Сначала изучи существующие компоненты проекта.
2. Не создавай дубликат существующего компонента.
3. Используй существующие design tokens.
4. Сохраняй существующую визуальную систему.
5. Применяй правила этого документа.
6. Проверяй mobile layout первым.
7. Затем проверяй tablet/desktop.
8. Добавляй все необходимые component states.
9. Добавляй accessibility.
10. Добавляй reduced-motion behavior.
11. Проверяй dark/light themes, если обе поддерживаются.
12. Не добавляй декоративные эффекты без UX-причины.
13. Не изменяй глобальную дизайн-систему ради одного экрана.
14. Если существующий интерфейс нарушает эти правила, исправляй его системно, а не локальными хаками.
15. Не менять бизнес-логику только ради визуального рефакторинга.
16. Не удалять существующий функционал при redesign.
17. При сомнении предпочитай стандартный, понятный и доступный interaction pattern.
